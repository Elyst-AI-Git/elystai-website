# Services page reference brief

*Prepared 29 August 2026. The live listai.com page was not reachable, so this audit uses the current working /services route and the approved website-page brief. No site code was changed.*

## Current page read

The working page has the strongest information architecture of the three: a clear hero, an honest “works when / does not work when” split, Audit → Build → Handover, a dark handover section, working-together rules, FAQ, and a single workflow CTA. The dark handover block is the right differentiator.

Visually, the page still repeats the same dither hero and then relies on long text lists. The buyer can understand the philosophy but cannot yet see a concrete engagement, an example workflow, the artefact produced at each phase, or where a pilot ends and paid integration begins. The page should sell a bounded operating model, not a catalogue of AI capabilities.

## Recommended changes, in order

1. **Turn each phase into input → work → output.** Audit: access and workflow evidence in; map, opportunity, risks, and measure out. Build: approved scope and real work in; tested system and exception paths out. Handover: trained users and owner in; runbook, access transfer, limits, and support terms out.
2. **Give Handover the most visual weight.** Use a simple ownership diagram: task enters → AI prepares → human reviews where needed → approved result is recorded → client owns the system.
3. **Add four example workflows, not generic service labels.** Start with UAE real-estate lead intake/triage, trade or logistics RFQ-to-brief, appointment-led service follow-up, and document/reporting workflows. Label them as examples to adapt, not guaranteed vertical products.
4. **Show the pilot boundary.** State that early work is one workflow, one owner, a bounded test, and one measure. Integrations, live sensitive data, and broader rollout require explicit scope.
5. **Keep the fit section.** The “does not work when” column is unusually credible. Add the human-review rule for high-risk decisions and lawful data access.
6. **Make pricing language operational.** Keep per-project/phased pricing, but show that the proposal includes scope, exclusions, milestones, measure, and payment phases. Do not publish a number until the open price-band decision is made.
7. **Use the CTA as a qualification step.** Ask for the workflow, owner, tools, approximate volume, and desired change. Do not send services traffic to a training-fit CTA.
8. **Differentiate the visual system.** Keep the dither on the homepage; use an annotated workflow or case strip on Services. The page needs to show how work moves, not just state that it will.

The Services page should make this easy to understand: *Elyst finds one workflow worth fixing, builds the smallest system that can prove it, and leaves the client able to run it.*
